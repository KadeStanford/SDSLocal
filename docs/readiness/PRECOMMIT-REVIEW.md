## Category-recovery migration review

`20261001000200_workspace_category_recovery.sql`:

- Requires signed-in, active **owner** membership; denies staff/unrelated users. Checks business-page feature access.
- Locks the business row, validates at most five unique active category IDs compatible with business type, rejects null/duplicate/unknown entries, then replaces memberships atomically. First category becomes primary and summary is rebuilt.
- Uses `SECURITY DEFINER` with empty `search_path` and schema-qualified objects. Revokes PUBLIC/anon execution; authenticated callers still face the explicit owner check.
- Allows clearing categories, consistent with the UI saying one is needed to publish; publication readiness must still enforce that later.
- The existing `ux_recovery.sql` fixture covers primary/readiness refresh, duplicate rejection without erasing old categories, and staff/unrelated-account denial. **Not executed today** because no local DB engine. Feature-helper/grant compatibility and real-role invocation remain unverified.

Recommendation: preserve and validate as a coherent UI/schema candidate. Its deployment-history receipt is absent; verify actual staging function definition before proposing a forward change. Do not execute its `CREATE OR REPLACE` on staging during this review.

## Customer-appointment-history migration review

`20261001000300_customer_appointment_history.sql`:

- Read-only `STABLE SECURITY DEFINER`, empty `search_path`; returns only appointments whose `customer_id` equals `auth.uid()` and requires non-null identity.
- Exposes a small summary (business/service names, times/timezone, status/payment status); omits provider credentials, contact details and guest status tokens. PUBLIC/anon execution is revoked and authenticated granted.
- History remains available independently of business listing visibility, which is sensible for existing customer obligations. This does not grant other users access.
- The screen uses a request generation and owner identity check, so stale async responses cannot display another account's snapshot. Guest bookings are read from locally saved capability tokens; failures are surfaced rather than silently treating all as successful.
- The pure customer-commitments tests cover history timing/status, safe filter construction and display helpers. `ux_recovery.sql` tests owner history, other-account isolation and null-identity output; **SQL/grant tests not rerun today**. REST row limits/pagination and native navigation still need acceptance.

Recommendation: sound static intent, pending user confirmation that this local addition is approved and disposable database/grant verification. Pair the migration and screen so a client isn't published against a missing RPC.
